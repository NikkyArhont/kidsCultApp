# Переходные правила — не окончательная защита

Эти файлы подготовлены для текущего, ещё не обновлённого мобильного клиента и
существующей админки. Они уменьшают доступ, но **не устраняют все уязвимости**.
Не использовать их как основание для запуска реальных платежей или заявления,
что данные детей изолированы. Cloud Functions и приложение не публиковались.

## Что копировать

- Firebase Console → Firestore Database → Rules: **полностью заменить** содержимое
  на `firestore.transition.rules`, не добавлять его к старому wildcard-правилу.
- Firebase Console → Storage → Rules: после Firestore использовать
  `storage.transition.rules`.
- Сначала сохранить предыдущие версии правил. Проверить на тестовом окружении
  вход, регистрацию администратора, смену имени, контент и загрузку изображений.
- Firestore-правила закрывают клиентское изменение `admins.status`. После этого
  проверить все существующие `admins` и сохранить `accept` только у подтверждённых
  владельцем администраторов. Пока старые открытые правила действуют, такой список
  может измениться после проверки. Нельзя доверять одному значению `accept` без
  сверки, кто именно получил его.
- Storage читает `admins/{uid}` из Firestore. При первой публикации Google может
  запросить разрешение на связь Storage Rules с Firestore — без него загрузки
  админки не будут работать. Не выдавать пользователям общий IAM-доступ к базе.
- Это не инструкция `firebase deploy`: общий deploy проекта не запускать.
  Публикация в рабочую консоль из этой задачи не выполнялась.

## Что закрывается

- Неавторизованный доступ к `users` и прочим данным приложения.
- Самоназначение администратора: клиент создаёт только свою заявку `wait`, может
  читать её и менять своё имя; одобрение/отзыв остаются в доверенной Console.
- Изменение игр, вопросов, уровней, статей и тарифов не одобренным администратором.
- Любой клиентский доступ к `phone_verifications`, `_otp_challenges`,
  `_otp_rate_limits`, `payment_intents`, включая вложенные документы.
- Клиентская запись SMS-конфига, доступ к неизвестным коллекциям и неизвестным
  путям Storage, изменение файлов `admins/` обычным пользователем.
- Запись/удаление файлов `users/{uid}/...` другим пользователем.

## Что намеренно пока НЕ закрывается

1. `config/sms_settings` остаётся доступен для чтения без входа. Это **небезопасно**,
   но старый клиент получает оттуда RedSMS-реквизиты и сам отправляет SMS. Запрет
   чтения без замены клиента ломает реальную доставку SMS. После перехода на
   `sendCodeSecure` удалить этот match, закрыть все старые auth-функции и сменить ключ.
2. `sendCodeDev` по-прежнему возвращает правильный OTP. Правила Firestore не могут
   запретить это: Admin SDK старой функции обходит клиентские Rules. Требуется
   согласованное отключение/переписывание самих `sendCodeDev`, `sendCodeProd`,
   `verifyCode` и обновление приложения. До этого вход остаётся уязвимым.
3. Любой вошедший пользователь всё ещё имеет широкий доступ к `users`, `tasks`,
   `bonuses`, `coin_changes`, `dairy`, `chats`, `notifications`, `orders` и их
   подколлекциям. Это сохраняет текущие запросы и записи, **но не защищает чужие
   профили, переписку, баллы или подписки от авторизованного нарушителя**.
4. Общие чтения файлов и записи `chats/` и `task/` сохраняются для совместимости.
   Групповая фотография загружается до создания Firestore-документа чата; проверка
   членства в ещё не созданном документе заблокировала бы создание группы.
5. Уже выданные download URL с токеном не становятся приватными от изменения
   этих правил. Отзыв таких URL — отдельная работа, не выполнялась.

Все эти исключения явно присутствуют в файлах и тестах. Это временное уменьшение
доступа, а не «готовые безопасные правила» для нового релиза.

## Почему окончательные правила нельзя просто вставить сейчас

- Старый SMS-клиент читает конфиг до авторизации; новый больше этого не делает.
- Старый платёжный клиент создаёт заказы и выдаёт подписку сам; новый использует
  сервер. Финальные правила должны запретить эти клиентские записи.
- Подсказки наставника запрашивают все задания (`initPopularTasks`), а рейтинг
  запрашивает документы пользователей. Rules не отфильтровывают скрытые документы
  или приватные поля — нужны подходящие запросы/отдельные публичные данные.
- Связи наставник–ребёнок, транзакции баллов и onboarding требуют проверки
  согласованных изменений документов, а не просто `request.auth != null`.
- Фото нового чата нужно привязать к загрузившему пользователю или сначала
  безопасно создать чат, затем загружать файл.

Следующий релиз должен убрать переходные исключения одновременно с обновлением
обоих клиентов/сервера, а не добавлять к ним ещё один `allow ...: if false`.
План: `../docs/HARDENING_ROLLOUT.md`.

## Локальные проверки

Из `security`, Node.js и Java должны быть доступны:

```sh
npm ci --ignore-scripts
npm test
```

Тесты используют только Emulator Suite с проектом `demo-kidscult-rules` и loopback
адресами. Они не вызывают облачные функции, не отправляют SMS и не меняют рабочую
базу. Не заменять `demo-kidscult-rules` на реальный проект.

Набор проверяет разрешённые и запрещённые операции, обход через batch, вложенные
документы, ожидаемые запросы старого клиента и явно оставшиеся широкие разрешения.

18.09.2026 проверка реально выполнена: **14 тестов прошли, 0 ошибок**; Firestore
Emulator 1.19.8 и Storage Rules Runtime 1.1.3 приняли оба файла. Эмуляторы после
проверки остановлены. Сообщения PERMISSION_DENIED в выводе соответствуют ожидаемым
отказам отрицательных тестов. Реальный IAM Storage↔Firestore и полный интерфейс
приложения этим запуском не проверялись.
