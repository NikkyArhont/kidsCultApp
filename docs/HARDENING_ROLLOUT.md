# Проверка и выпуск исправлений

Изменения кода подготовлены локально; функции и секреты не развёрнуты.
Пользователь сообщил, что вручную применил переходные Firestore/Storage Rules,
но опубликованные версии ещё не сверены с локальными файлами. Без staging-проверки
и сведений о действующей конфигурации выпуск не считается готовым.

## Что изменено

- Исправлены переход со splash, чтение кешированного пользователя, обработка
  аргументов маршрутов и пути создания заданий по ролям.
- Firestore/FCM-подписки отменяются и очищаются между сессиями; события прежнего
  пользователя не должны менять состояние новой сессии.
- Статус задания/бонуса, баллы и история записываются одной транзакцией;
  повторная операция не начисляет или списывает их заново. Возврат получает
  ребёнок, оплативший бонус. Клиентская транзакция **не заменяет** Firestore Rules.
- OTP генерируется, отправляется и проверяется сервером. Клиент не получает
  RedSMS-реквизиты и правильный код, не логирует токены.
- Платёжный сервер берёт цену тарифа, проверяет владельца заказа, сверяет объект
  с ЮKassa и атомарно выдаёт подписку ровно один раз.

## 1. Зафиксировать baseline

Проект `kidscult-a5d7e` подтверждён пользователем и конфигурацией отдельной админки.
Пользователь предоставил Firestore/Storage Rules, скриншот списка функций и архивы
старой авторизации. Результат проверки — в [FIREBASE_BASELINE.md](FIREBASE_BASELINE.md).
Архивы содержат реквизиты: оставлены локально и исключены из Git, не предназначены
для повторного deploy или публикации.

По предоставленному скриншоту все функции находятся в `us-central1`:
`initialPayment`, `ukassaWebHook`, `sendPushNotificationToUser`, `sendReminders`,
`checkOverdueTasks`, `checkOverdueTasksTest` — v2; `sendCodeDev`, `sendCodeProd`,
`verifyCode` — v1. Платёжные функции не требуют перехода Gen1 → Gen2.
Новая авторизация использует отдельные имена v2, а старые функции требуют
отдельного согласованного отключения. Не удалять функции ради обхода ошибки deploy.

До переключения ещё нужны индексы, проверка UID тестовых аккаунтов, список
легитимных администраторов, конфигурация scheduler/IAM и сверка заказов.
Предположение пользователя об отсутствии реальных оплат не заменяет сверку.
Не запускать общий `firebase deploy`, который может затронуть другие функции.
Сохранить экспорт правил и резервную копию рабочих данных.

## 2. SMS-сервер

Новые экспорты: `sendCodeSecure` и `verifyCodeSecure`. Secret Manager:

15 предоставленных тестовых пар телефон/код находятся только в локальном файле
`functions/qa_phone_codes.local.json`, исключённом из Git. Для работы на Android
и iOS их нужно загрузить в Secret Manager проекта `kidscult-a5d7e` под именем
`AUTH_TEST_PHONE_CODES`, затем развернуть `sendCodeSecure` и новую сборку клиента.
Тестовый номер проходит обычный одноразовый challenge со сроком, лимитом повторной
отправки и проверкой заблокированного аккаунта, но SMS не отправляется. Эти пары
нужно считать тестовыми учётными данными, не хранить на аккаунтах реальные личные
данные и сменить/отозвать после тестирования. Для остальных номеров код случайный
и уходит по SMS. Настройка тестовых телефонов в Firebase Authentication не влияет
на этот собственный custom-token поток.

Загрузка секрета через Firebase CLI (из корня Flutter-проекта):

```sh
firebase functions:secrets:set AUTH_TEST_PHONE_CODES --project kidscult-a5d7e --data-file functions/qa_phone_codes.local.json
```

После настройки остальных секретов и проверки отправителя разворачивать только
новые функции авторизации (не весь код из папки, где есть изменённые платежи):

```sh
firebase deploy --config firebase.auth-deploy.json --project kidscult-a5d7e --only functions:sendCodeSecure,functions:verifyCodeSecure
```

Затем собрать и установить новую мобильную версию, которая вызывает эти два
имени. Не выключать старые функции до обновления установленных клиентов.

Перед запуском проверить, что в рабочем проекте нет настоящих пользователей с
этими UID или номерами, и убедиться, что опубликованные правила не дают тестовым
аккаунтам доступа к чужим данным. Текущие переходные правила **ещё дают такой
доступ** любому вошедшему пользователю, поэтому включать тестовые аккаунты до
окончательных правил нельзя считать безопасным выпуском. Нельзя просто развернуть
функцию при старой сборке: она продолжит вызывать `sendCodeDev` и пытаться
отправлять SMS сама. Новая сборка уже вызывает `sendCodeSecure`.

- `REDSMS_LOGIN` — логин аккаунта;
- `REDSMS_API_KEY` — новый ключ, недоступный клиенту;
- `OTP_HMAC_KEY` — случайный секрет не короче 32 символов, отдельный от SMS-ключа.

Параметр `REDSMS_SENDER` по умолчанию `FamilyCult`, как в реально отправляющем SMS
мобильном клиенте. Архивная `sendCodeDev` указывала `KidsCult`, но использовала
`test: true`, поэтому это не подтверждает разрешённое имя для настоящих SMS.
Перед открытием нового входа обычным номерам сверить `FamilyCult` с действующим
кабинетом провайдера и при необходимости явно настроить `REDSMS_SENDER`.
Функции читают Secret Manager, а не `config/sms_settings`.
Проверить права runtime service account на секреты и создание Firebase custom token
(`signBlob`/Service Account Token Creator в соответствии с настройками проекта).

Код действует 5 минут и допускает 5 неверных попыток. Отправка: раз в 60 секунд,
не более 5 в час на номер, 20 в час на IP и 500 в сутки на проект. Подтвердить
ограничения по реальной нагрузке. Ошибки провайдера также расходуют квоту.
Проверить доверенную цепочку прокси: `rawRequest.ip` может зависеть от присланного
`X-Forwarded-For`, поэтому IP-лимит не заменяет телефонный/общий бюджет и защиту
на ingress. Не выбирать число доверенных proxy hops без проверки окружения.
Можно настроить Firestore TTL по `cleanupAt`; проверка срока OTP не зависит от TTL.

`AUTH_ENFORCE_APP_CHECK` по умолчанию false для совместимости. Включить после
регистрации App Check на всех платформах и проверки токенов. При выключенном
App Check лимиты не являются полной защитой от распределённой SMS-атаки;
контролировать расходы и квоты провайдера.

UID берётся из авторитетной привязки телефона Firebase Auth, иначе применяется
старый формат `phone_<цифры>`. Архивная `verifyCode` формирует UID как `phone_${phone}`
без нормализации; мобильный клиент передаёт цифры без `+`. Для этого пути формат
подтверждён и проверен тестом сохранения существующего аккаунта без phone binding
в Firebase Auth. Если существовали сторонние клиенты с иным форматом, проверить их
UID отдельно. При двух разных учётных записях сервер отказывает вместо неявного
слияния. Редактируемое клиентом поле `users.phone` не является основанием для
выбора аккаунта.

После перехода отключить или безопасно обновить все три старые функции:
`sendCodeDev`, `sendCodeProd`, `verifyCode`. Новые функции не закрывают старую
доступную функцию, возвращающую OTP. Закрыть клиентский доступ к старой коллекции
`phone_verifications`: её документы содержат код открытым текстом, а `verifyCode`
не проверяет срок действия. Новая авторизация эту коллекцию не использует.
Согласовать обязательное обновление старых клиентов, иначе они потеряют вход.
Отозвать прежний RedSMS API-ключ и закрыть клиентское чтение `config/sms_settings`.

## 3. Правила доступа

Предоставленные пользователем правила открывают `users` всем без входа, остальные
документы — любому авторизованному пользователю. В Storage любой авторизованный
пользователь имеет доступ ко всем путям. Эти правила нельзя считать безопасной
основой для выпуска. Подготовлены только явно переходные файлы
`security/firestore.transition.rules` и `security/storage.transition.rules`,
сохраняющие небезопасные исключения старого клиента. Ограничения и тесты описаны
в [security/README.md](../security/README.md). Окончательные правила пока не готовы:
необходимо изменить несовместимые операции и проверить общую матрицу доступа
мобильного приложения и отдельной админки. Требования для окончательных правил:

- Полностью запретить клиентский доступ к `_otp_challenges`, `_otp_rate_limits`,
  `phone_verifications`, `payment_intents` и секретному `config/sms_settings`.
- Тарифы разрешать читать, изменять только серверу/администратору.
- Заказы создавать/изменять только серверу; чтение — плательщику и получателю,
  с сохранением запросов истории подарков старого формата.
- Не разрешать клиенту менять `premium_subscription`, `premium_subscription_ref`,
  `banned` и серверные полномочия. Учесть, что регистрация наставника пока записывает
  `trial_subscription` на клиенте: нужно ограниченное правило однократного trial
  либо серверный onboarding до общего запрета.
- Для транзакций баллов проверять участника, переход статуса, прежний баланс,
  сумму и связанную историю через `getAfter`. Новые поля: `tasks.reward_credited`,
  `bonuses.purchased_points`, `purchased_kid`, `points_refunded`. Проверить allowlist.
- Проверить доступ к дневнику, чатам и файлам ребёнка независимо от UI.
- Учесть отдельную админку `C:/Users/snick/apps/kidsKultWeb/child_tracker_web-main`:
  вход email/password, решение о допуске по `admins/{auth.uid}.status == 'accept'`.
  Регистрация создаёт свой документ со `status: 'wait'` и `role: 'admin'`; роль
  сама по себе не даёт полномочий. Разрешить ожидание одобрения и редактирование
  собственного имени, но запретить клиентское изменение статуса/роли и создание
  сразу одобренного администратора. Одобрение остаётся в доверенной Console.
- Перед доверием существующим `admins` вручную сверить их: прежние правила позволяли
  любому вошедшему пользователю назначить себе `status: 'accept'`. Не считать
  содержимое этой коллекции автоматически достоверным.
- Одобренным администраторам нужны операции с `games`, `quizzes`, `levels`,
  `articles`, обращениями поддержки и файлами `admins/`. Не выдавать им через
  общий wildcard доступ к OTP, платёжным намерениям и секретам.

`allow ...: if false` в одном match **не отменяет** разрешение другого совпавшего
wildcard. Удалить перекрывающие общие разрешения. Проверить правила в Emulator
Suite как для разрешённых, так и для чужих документов.

Полный перенос балансов и onboarding на сервер — этап после проверки общей модели
доступа. Текущие транзакции обеспечивают согласованность, но сами по себе не защищают
от подделки запросов модифицированным клиентом.

## 4. Платежи

Следовать [PAYMENTS.md](../functions/PAYMENTS.md): настроить секреты, webhook и
return URL, закрыть клиентские записи, сверить старые заказы. Удаление ключа
из файлов не отзывает его и не очищает историю Git — нужна ротация.
Старые заказы не мигрируются автоматически из-за неверного ID и отсутствия
признака выданной подписки. Не начислять и не списывать повторно без сверки.

Демонстрационная iOS-ветка считала открытие purchase sheet успешной покупкой.
Она теперь сообщает о недоступности до списания; для включения нужны серверная
проверка Apple transaction/receipt и восстановление покупок. Это ограничение
текущего исправления, а не готовая IAP-интеграция.

## 5. Staging-проверки

На отдельном Firebase-проекте и тестовом магазине пройти:

1. Новый и существующий пользователь: вход, повтор SMS, неверный/просроченный код,
   бан, незавершённая регистрация, logout/login другой ролью.
2. Фильтры заданий/бонусов, смена вкладок, события после logout, foreground push
   с последующим нажатием, запуск приложения из push.
3. Два устройства: одновременно подтвердить задание, купить бонус, отклонить
   получение; проверить одну запись истории и правильный баланс ребёнка.
4. Подписка и подарок: успех, отмена, закрытие приложения, повтор webhook,
   потеря сети до/после оплаты, отказ capture, повторная проверка статуса.
5. Чат, дневник, профиль и файлы с новыми Rules: свои операции проходят, чужие — нет.

Локальные тесты используют двойники; они не проверяют deployed IAM, индексы,
Rules, устройства, SMS-доставку или магазин. После staging переключать сервер,
правила и клиенты согласованно.
