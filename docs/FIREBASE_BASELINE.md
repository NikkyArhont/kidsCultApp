Сведения из предоставленных пользователем скриншотов, правил и локальных исходников.
Рабочая консоль и облачные данные при этой проверке не изменялись.

## Архивы авторизации

`cloudFunctions/sendCode.zip`, `sendCodeDev.zip`, `sendCodeProd.zip` идентичны.
SHA-256 каждого: `d64b133d69bbec3d5c45f674f2b22e14e7de8f73317546630f478e9f5c04e888`.
В каждом один `index.js` с экспортами `sendCodeDev`, `sendCodeProd`, `verifyCode`.
Поэтому отсутствие архива с названием `verifyCode.zip` не означает отсутствия кода.
Архивы не распаковывались в исходники и не запускались.

Подтверждено по коду:

- UID: `phone_${phone}`. Клиент передаёт очищенный номер без `+`; новый backend
  сохраняет `phone_<цифры>`. Аккаунты нестандартных клиентов требуют отдельной сверки.
- Оба SMS-обработчика используют отправителя `KidsCult`; новый default приведён
  к этому значению. При этом исходный мобильный клиент после `sendCodeDev` сам
  отправляет настоящее SMS с именем `FamilyCult`, читая ключ из `config/sms_settings`
  до авторизации. Архивная DEV-отправка тестовая. Перед новым выпуском явно настроить
  имя, реально разрешённое провайдером; один архив не подтверждает это имя.
- `sendCodeDev` использует тестовую отправку и возвращает правильный OTP в ответе.
- В `phone_verifications/{phone}` хранится открытый код; старый `verifyCode`
  не проверяет возраст кода, а проверка и удаление выполняются отдельно.
- Счётчик попыток, ограничение повторной отправки и выдача токена не образуют
  единой транзакции. Конкурентные вызовы могут обходить предполагаемые ограничения.
- В исходниках есть жёстко прописанные реквизиты RedSMS и логирование входных данных
  с кодом. Значения реквизитов здесь не копируются; их действительность не проверялась.
- Пакет legacy-функций использует Node 18, firebase-functions ^4.3.1,
  firebase-admin ^11.8.0. Его нельзя подменять новым пакетом без согласованного выпуска.

Архивы исключены из Git через `.gitignore`, но остаются на диске. Это не отзывает
реквизиты и не заменяет их ротацию. `.runtimeconfig.json` также исключён из Git.

## Отдельная админка

Исходники: `C:/Users/snick/apps/kidsKultWeb/child_tracker_web-main`.
Проверена только интеграция с Firebase; файлы админки не изменены.

`lib/main.dart` и `.firebaserc` указывают на тот же `kidscult-a5d7e`.
Web App ID `1:419315761443:web:668c95b300e6afa8b78c96` совпадает со скриншотом
KidsCultAdmin. MiniApp — другой Web App; его фактическое использование неизвестно.

Вход: Firebase Auth email/password. `AuthCubit.signIn` и splash допускают
пользователя по `admins/{uid}.status == 'accept'`. При регистрации создаются
`status: 'wait'` и `role: 'admin'`; одного поля role недостаточно для допуска.
Одобрение пользователь меняет вручную в Firebase Console.

Обращения к данным, которые нужно сохранить в новых правилах:

| Область | Операции клиента админки |
| --- | --- |
| `admins/{uid}` | Создание своей заявки, чтение/наблюдение своего статуса, изменение имени |
| `games`, `quizzes` | Чтение, создание и редактирование; архивирование игр |
| `levels`, `articles` | Чтение, создание, редактирование, смена порядка, архивирование и удаление |
| `chats` и `messages` | Список обращений поддержки, чтение и отправка сообщений, изменение last_message |
| `users` | Чтение профиля участника обращения поддержки |
| Storage `admins/…` | Загрузка контентных файлов и получение URL; сервис также содержит удаление по URL |

Регистрация пишет поле `profle_filled` с опечаткой, модель читает `profile_filled`:
учесть при проектировании allowlist, не блокировать существующий payload молча.
В ChatCubit есть как запрос с `type == 'support'`, так и метод без ограничения type;
проверить фактические вызовы перед ограничением query в правилах.

Предоставленные общие правила разрешают авторизованному пользователю редактировать
любую запись `admins`. Перед вводом проверки статуса нужно вручную проверить
легитимность уже одобренных записей. Новые правила должны сохранять регистрацию
в ожидание одобрения, но не позволять самому назначать или изменять полномочия.
